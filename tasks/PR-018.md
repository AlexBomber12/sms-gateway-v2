# PR-018: Narrow AppArmor Sms member wildcard to least-privilege

Branch: feat/pr-018-apparmor-sms-narrow
- Type: config
- Complexity: low
- Depends on: none
- Priority: 5
- Coder: codex

## Problem

The custom AppArmor profile `deploy/apparmor/sms-gateway-v2` introduced in PR-014 contains a broader-than-necessary D-Bus permit rule:

```
dbus (send)
  bus=system
  path=/org/freedesktop/ModemManager1/SMS/**
  interface=org.freedesktop.ModemManager1.Sms
  member=*,
```

The application code never calls any method on the `org.freedesktop.ModemManager1.Sms` interface itself. Reading SMS properties (Number, Text, Timestamp, PduType) is done via `org.freedesktop.DBus.Properties` (already permitted by a separate rule in the profile). Deleting an SMS goes through `org.freedesktop.ModemManager1.Modem.Messaging.Delete`, not through the per-Sms interface (also already permitted by a separate rule).

The wildcard was a defensive overshoot during PR-014 development. With the production deployment now stable and verified (real SMS delivered with text correctly parsed and queue items deleted via the Messaging interface), the narrower posture can be confirmed safe.

The SMS interface defines methods like `Send` (used to send outgoing SMS), `Store` (move between storages), and a few state-modifying operations. None are called by sms-gateway-v2 today and none have a planned use in this read-only relay design.

## Scope

Remove the wildcard send rule for `interface=org.freedesktop.ModemManager1.Sms`. Profile continues to allow `Properties` reads and `Modem.Messaging.{List,Delete}` calls, which is the full set of operations the application actually performs.

Out of scope: any other AppArmor rule changes, any D-Bus rule changes elsewhere in the profile, replacing `**` path wildcards with narrower patterns (those are correct: `/Modem/**` matches future modem indices like `/Modem/1`, which is intentional).

## Files to modify

- `deploy/apparmor/sms-gateway-v2`

## Implementation notes

Remove the entire 5-line block that begins with `dbus (send)` and contains `interface=org.freedesktop.ModemManager1.Sms` plus `member=*`. Surrounding rules stay intact: the `Modem.Messaging.{List,Delete}` rule above it and the `dbus (receive)` rules below it are correct and necessary.

Add a short comment block above the remaining D-Bus send rules clarifying which interfaces the relay actually uses, so a future maintainer does not "restore" the wildcard rule under a misapprehension that it is needed:

```
# The relay only needs:
#   - DBus.Properties on Sms objects to read Number/Text/Timestamp/PduType
#   - Modem.Messaging.{List,Delete} to enumerate and remove processed SMSes
#   - Modem.Reset for the watchdog reset path
# It never calls methods on the org.freedesktop.ModemManager1.Sms interface.
# If a future feature requires sending or storing SMS, narrow rules for those
# specific members must be added here, not a member=* wildcard.
```

The comment goes inside the profile body (AppArmor accepts `#` line comments).

After the change, recreate the container on the production host and verify no fresh `apparmor="DENIED"` entries appear in `dmesg | grep -i apparmor | tail -20` over 24 hours of normal operation, including at least one SMS receive cycle.
