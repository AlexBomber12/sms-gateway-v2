# PR-027: Apply text-wait pattern to startup drain path

Branch: fix/pr-027-drain-uses-read-message
- Type: bugfix
- Complexity: medium
- Depends on: PR-025
- Priority: 3
- Coder: codex

## Problem

Verified by reading `src/sms_gateway_v2/modem/client.py` line 408 to 442 (`list_messages`) and comparing to `read_message` at line 444+. `list_messages` reads the `Text` property synchronously with `await self._read_required("Text", sms.get_text)` inside the message construction (line 428). There is no subscribe-and-wait pattern, no polling loop, no timeout. If the modem has an SMS in storage whose Text is still being decoded by ModemManager, `list_messages` will return that SMS with `text=""`.

`_drain_existing_messages` in `relay.py` calls `list_messages` at startup and processes each returned item through `_process_sms`, which enqueues and deletes. In steady state this is not a problem because SMS have been in storage long enough for decoding to complete. In one specific scenario it is a problem: if the container is restarted within the 10 to 15 second decode window after an SMS arrival, the drain reads Text as empty and the SMS is delivered to Telegram with sender-only body.

This is the same class of bug as PR-025 fixed for the MessageAdded path, on a different code path. Since PR-025 introduces empty-text rejection in `TelegramMessage.from_sms`, an empty-text SMS surfaced via drain would now fail Telegram build and enter the queue as a failed item. That is functionally better than delivering an empty message, but the SMS content is still lost because it has been deleted from EC25 storage after the failed enqueue.

## Scope

Route the drain path through `read_message` (which applies subscribe-and-wait pattern and returns None on undecoded Text) instead of the raw `list_messages`. Combine with the PR-025 retry orchestration so drain-discovered undecoded SMS enter the same bounded-retry flow as MessageAdded-triggered SMS.

Out of scope:
- Changing the `list_messages` API. It remains a lower-level primitive that returns whatever the modem currently reports. It is still useful for diagnostics.
- Adding new metrics or new log events beyond what PR-025 already introduces.
- Changing the drain trigger (still at startup, still before MessageAdded subscription).

## Implementation notes

### Step 1: Expose an SMS-path enumeration helper on the client

`list_messages` currently does two things: enumerate SMS paths on the messaging interface, and read each one. Split the enumeration into a public method that returns just the paths:

```
async def list_sms_paths(self) -> list[str]:
    modem_path = await self._ensure_modem_path()
    _, messaging = await self._get_messaging_interface(modem_path)
    return await self._read_required("Messages", messaging.get_messages)
```

Keep `list_messages` as it is today for callers that want the direct raw read (may be used in tests, in ad-hoc diagnostics, or in future feature work). Do not delete it.

### Step 2: Change drain to iterate paths via read_message

In `relay.py`, `_drain_existing_messages` currently calls `list_messages` and iterates over `IncomingSms` objects. Change to call `list_sms_paths` and for each path invoke `read_message(path)`. Handling per-item:

- `read_message` returns a populated `IncomingSms`: proceed as today (enqueue, delete).
- `read_message` returns None: the SMS is undecoded. Delegate to the PR-025 retry orchestrator via the same helper `_on_new_sms` uses. Do not enqueue, do not delete. The retry will either recover Text on a later attempt or, on exhaustion, delete the SMS and increment the undecoded metric.

Add a top-level log event `relay_drain_completed` (already exists) with an additional field `count_scheduled_retry` alongside the existing `count_drained`. Both fields are informational.

### Step 3: Concurrency and ordering

Drain currently processes items serially. Preserve that: iterate paths in the same sorted order the previous `list_messages` produced (that ordering is defined by `_message_sort_key`). Sort the paths returned by `list_sms_paths` via a lightweight helper that reads the timestamp for ordering, or defer ordering until after `read_message` is called and sort the successful results. Whichever preserves the existing arrival-order semantics is acceptable; document the choice in an inline comment.

Do not launch retries in parallel with drain. If drain schedules a retry via PR-025 orchestration, that retry runs asynchronously afterward. Drain completes as soon as all paths have been dispatched to either enqueue or retry.

### Step 4: Interaction with PR-025 shutdown handling

PR-025 registers pending retries in `self._pending_text_retries` and cancels them on relay shutdown. Drain-scheduled retries land in the same registry and share the same cancellation behavior. No new shutdown handling needed here.

4. `test_drain_schedules_retry_when_read_message_returns_none`: mock `read_message` returning None for one of the paths. Verify a retry is scheduled via the PR-025 orchestrator for that path. The other path proceeds normally.

6. `test_drain_preserves_message_ordering`: three paths returned in arbitrary order. Successful enqueues occur in the sort order defined by `_message_sort_key` (timestamp asc).

7. `test_drain_scheduled_retries_are_cancelled_on_shutdown`: verify drain-scheduled retries are in `_pending_text_retries` and get cancelled by relay stop.
