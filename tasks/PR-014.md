# PR-014: Replace AppArmor unconfined with narrow custom profile

Branch: feat/pr-014-apparmor-profile
- Type: config
- Complexity: high
- Depends on: PR-013
- Priority: 4
- Coder: codex

## Problem

PR-010 unblocked production deployment by setting `security_opt: [apparmor=unconfined]` on the sms-gateway-v2 container. This trades AppArmor mediation away wholesale: the container now has no profile at all, equivalent to a host process for AppArmor purposes. The trade was acceptable as a fix because the container was already trusted to talk to the system D-Bus and to the modem, both of which are privileged. But "no profile" is strictly weaker than "narrow profile that allows exactly what the application needs."

The right long-term posture is a custom AppArmor profile that:

1. Inherits the spirit of `docker-default` (deny most filesystem write paths, deny ptrace of host, deny capability escalation).
2. Explicitly permits the D-Bus operations the application actually performs:
   - `dbus send` to `org.freedesktop.DBus` for SASL handshake / Hello / NameOwnerChanged.
   - `dbus send` to `org.freedesktop.ModemManager1` for `Introspectable`, `Properties`, `ObjectManager`, the `Messaging` interface, the `Modem` interface, and the `Sms` interface.
   - `dbus receive` to subscribe to PropertiesChanged, MessageAdded, NameOwnerChanged.
3. Allows the application to read the bind-mounted D-Bus socket.

## Scope

Author a custom AppArmor profile, ship it under `deploy/apparmor/`, document the operator install steps in `docs/deploy.md`, and switch `deploy/docker-compose.yml` from `apparmor=unconfined` to `apparmor=sms-gateway-v2`.

Out of scope: profile-as-policy enforcement testing in CI (would require host-level AppArmor in GitHub Actions runners; this is operator-verified only). Out of scope: hardening the profile beyond D-Bus mediation (e.g., further restricting filesystem paths inside the container — the application uses very few, but profiling that needs runtime data, not theory).

## Files to modify

- `deploy/apparmor/sms-gateway-v2` (new — the profile body)

## Implementation notes

Profile structure: derive from the upstream `docker-default` profile shipped with the AppArmor packages on Ubuntu, then add D-Bus permit rules. Use the `abi <abi/3.0>,` declaration so the profile is portable across recent kernel versions. Profile name: `sms-gateway-v2`.

D-Bus rules. Add explicit `dbus (send)` rules for:

- `bus=system path=/org/freedesktop/DBus interface=org.freedesktop.DBus member={Hello,AddMatch,RemoveMatch,GetNameOwner,NameHasOwner,RequestName,ReleaseName}`
- `bus=system path=/org/freedesktop/ModemManager1 interface=org.freedesktop.DBus.{Introspectable,Properties,ObjectManager}`
- `bus=system path=/org/freedesktop/ModemManager1/{Modem,Sms,SIM,Bearer}/** interface=org.freedesktop.DBus.{Introspectable,Properties}`
- `bus=system path=/org/freedesktop/ModemManager1/Modem/** interface=org.freedesktop.ModemManager1.Modem.Messaging member={List,Delete}` (the actions polkit gates with PR-013's rule)
- `bus=system path=/org/freedesktop/ModemManager1/Sms/** interface=org.freedesktop.ModemManager1.Sms member=*`

Add `dbus (receive)` rules for the matching paths and signals (`PropertiesChanged`, `Added`, `NameOwnerChanged`).

Filesystem rules: keep docker-default's denies. Add explicit reads for `/var/run/dbus/system_bus_socket` and `/run/dbus/system_bus_socket` (via the bind mount). Container application files under `/app` are already read via the docker-default's broad `r` for non-write paths.

Operator install procedure documented in `docs/deploy.md`:

1. Copy the profile to host: `sudo install -m 0644 deploy/apparmor/sms-gateway-v2 /etc/apparmor.d/sms-gateway-v2`.
2. Load the profile: `sudo apparmor_parser -r -W /etc/apparmor.d/sms-gateway-v2`.
3. Verify it appears in `sudo aa-status | grep sms-gateway-v2`.
4. Recreate the container: `cd deploy && docker compose -p sms-gateway-v2 up -d --force-recreate`.
5. After ~30 seconds, check `dmesg | grep audit | tail -50` for any `apparmor="DENIED"` lines that mention `sms-gateway-v2`. Each denial indicates a missing rule and is reported back upstream as a follow-up PR.

The compose change in `deploy/docker-compose.yml` is one line: replace `apparmor=unconfined` with `apparmor=sms-gateway-v2`.

Document a clear escape hatch in the same docs section: if the custom profile breaks something operationally and the operator needs the application back online while debugging, they can `apparmor=unconfined` on the host's compose file (uncommitted) and continue. This is the same pre-PR-014 posture and remains safe for short windows.
