# PR-013: Polkit rule and group_add to enable SMS delete from container

Branch: fix/pr-013-polkit-messaging-delete
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 1
- Coder: codex

## Problem

The container's SMS delete operation (`org.freedesktop.ModemManager1.Modem.Messaging.Delete`) consistently fails on the production host (NAS, Ubuntu 24.04) with:

```
dbus_fast.errors.DBusError: Unauthorized: PolicyKit authorization failed:
not authorized for 'org.freedesktop.ModemManager1.Messaging'
```

Reproduction: when `_drain_existing_messages` runs at relay startup with `fail_on_delete_error=True`, any SMS still in modem storage (e.g. left over from a previous run that itself could not delete) causes the entire startup to fail. The container then enters a restart loop because the lifespan context raises and uvicorn exits.

Root cause: polkit (action `org.freedesktop.ModemManager1.Messaging`) is configured by default to require admin authentication, which an SSH or container session cannot satisfy because no graphical authentication agent is present. Even commands run by `alexey` interactively over SSH are denied; only `sudo mmcli ...` (root override that bypasses polkit) currently works on the host. The container running as uid 1000 has no path through this policy at all.

Recovery from this state currently requires running `sudo mmcli -m 0 --messaging-delete-sms=N` on the host before the container can start cleanly. This is an unacceptable operational burden because every host reboot, kernel update, or stale SMS in storage will recreate the deadlock.

## Scope

Grant the container's user the rights it needs to call `org.freedesktop.ModemManager1.Messaging` actions (delete, list, etc.) without admin authentication, by:

1. Defining a Linux group `sms-gateway` on the host (operator step, documented).
2. Adding a polkit JavaScript rule that grants `result = polkit.Result.YES` to subjects in that group for the relevant ModemManager actions, with no admin prompt.
3. Adding `group_add` to the deploy compose file so the container process belongs to that group from the kernel's perspective and polkit's `pkcheck` sees the supplementary group on the peer process.

This is the same pattern documented in `docs/deploy.md` under the polkit section (added in PR-005); this PR makes the recommendation real.

Out of scope: replacing polkit-based authorization with a different mechanism (e.g. running container as root, broadening D-Bus policy directly). Both are weaker security postures than a narrowly-scoped polkit rule.

## Files to modify

- `deploy/docker-compose.yml` (add `group_add: ["sms-gateway"]`)
- `docs/deploy.md` (replace the conceptual polkit section with concrete operator steps and the rule body)
- `deploy/polkit/10-sms-gateway.rules` (new file, operator copies to host `/etc/polkit-1/rules.d/`)

## Implementation notes

Polkit rule body. The file `deploy/polkit/10-sms-gateway.rules` ships in the repo as a reference; the operator copies it to `/etc/polkit-1/rules.d/10-sms-gateway.rules` on the host. The rule grants ALL actions starting with `org.freedesktop.ModemManager1.` to subjects in the `sms-gateway` group, returning `polkit.Result.YES` (no auth prompt). This is intentionally broad to cover not just Messaging but also any future Modem action that polkit might gate. If we later need to narrow it, the rule has a single source of truth and is easy to audit.

The rule MUST use the `unix-group` form for matching (works for any uid, including the container's uid 1000 which the host does not need to know about by name) and not the `unix-user` form. The rule MUST be a single conditional inside `polkit.addRule` that returns `Result.YES` only on a positive group match and otherwise falls through (returns nothing).

In `deploy/docker-compose.yml`, add `group_add: ["sms-gateway"]` to the service. The Linux GID must exist on the host before the container starts; document this as a prerequisite. Do NOT hardcode a numeric GID in compose; use the group name string, which docker resolves at container start by querying the host's `/etc/group`.

In `docs/deploy.md`, the polkit section must include:

1. The exact command to create the host group: `sudo groupadd --system sms-gateway`.
2. The exact command to install the rule: `sudo install -m 0644 deploy/polkit/10-sms-gateway.rules /etc/polkit-1/rules.d/`.
3. A note that the polkit daemon picks up the rule on its next restart or after a host reboot; for immediate effect, `sudo systemctl restart polkit`.
4. A verification step: from inside a temporary container with `--group-add sms-gateway --user 1000:1000`, run `mmcli -m 0 --messaging-list-sms` and `mmcli -m 0 --messaging-delete-sms=0` (only the latter exercises the polkit-protected path; the former is unprotected). Both should succeed.
5. Cross-reference to PR-014 (custom AppArmor profile, future) so that operators who later harden the AppArmor side know not to break this group_add by changing the profile.

## Tests

No application code is changed; no unit or integration tests apply. The existing CI continues to pass unchanged.

Operational verification belongs in the post-merge runbook, not in CI:

1. Operator creates the host group, installs the rule, restarts polkit.
2. Operator pulls and recreates the container with the new compose.
3. With at least one SMS in modem memory, the container starts cleanly: drain processes the SMS, deletes it, no `relay_sms_delete_failed` warnings in logs.
4. `mmcli -m 0 --messaging-list-sms` shows the SMS gone after relay processed it.
