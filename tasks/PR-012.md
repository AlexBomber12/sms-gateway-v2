# PR-012: GitHub Actions workflow to build and push container image to ghcr.io on main

Branch: feat/pr-012-ghcr-build-push
- Type: config
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: codex

## Problem

The deployment workflow currently requires building the container image manually on each target host (the NAS, in production at 192.168.50.2). Existing CI runs ruff, mypy, and pytest with 100 percent coverage but does not build a container image, and the image tag `ghcr.io/alexbomber12/sms-gateway-v2:latest` referenced by `deploy/docker-compose.yml` is never published to ghcr.io.

This means:

- Every merge to main is followed by a manual `git pull && docker build` cycle on the NAS before `docker compose up -d --force-recreate` can pick up the new code.
- A fresh deployment on a different host requires the full clone-and-build flow rather than a simple `docker compose pull`.
- There is no immutable, pinnable image artifact for any given commit. If something regresses on main, the operator has no published image to roll back to without rebuilding from a tagged commit.

## Scope

Add a GitHub Actions workflow that builds the container image on every push to `main` and on every published release tag, and publishes the resulting image to ghcr.io.

Authentication uses the workflow's built-in `GITHUB_TOKEN` with `packages: write` permission. No secrets need to be added to repo settings.

Tagging strategy:

- On push to `main`: publish `ghcr.io/alexbomber12/sms-gateway-v2:latest` and `ghcr.io/alexbomber12/sms-gateway-v2:sha-<short-sha>`.
- On release tag `v*`: publish `ghcr.io/alexbomber12/sms-gateway-v2:<tag>` AND update `:latest`.

Out of scope: signing images with cosign, multi-arch builds (the only consumer is amd64 on x86_64 NAS), SBOM generation, vulnerability scanning. These are reasonable later additions but they are not the bottleneck right now.

## Files to modify

- `.github/workflows/build-and-push.yml` (new)
- `docs/deploy.md` (small doc update describing how to consume the published image)

## Implementation notes

Use the standard pattern for GHCR publishing:

1. Triggers: `push` on branches `[main]` and `tags ['v*']`. Also include `workflow_dispatch` for manual builds.
2. Permissions block at job level: `contents: read`, `packages: write`.
3. Steps: checkout → set up Buildx → log in to ghcr.io with `${{ github.actor }}` and `${{ secrets.GITHUB_TOKEN }}` → build and push using `docker/build-push-action@v5` (or current stable).
4. Tags: use `docker/metadata-action@v5` to compute the tag set from the trigger; configure it to emit `latest` only on default branch and on tag pushes (not on PRs, not on feature branches).
5. Cache: enable BuildKit layer cache via `cache-from: type=gha` and `cache-to: type=gha,mode=max`. The first build will be cold; subsequent builds will reuse the apt-get and pip layers.
6. Job name: `build-and-push`. Workflow name: `build-and-push`.
7. The workflow MUST NOT run on pull requests opened by external forks (default behavior is fine — `push` does not fire for PR events; do not add a `pull_request` trigger).

The existing `ci.yml` workflow stays untouched. Tests and linters continue to gate PRs; image publishing happens only after merge.

In `docs/deploy.md`, add a short subsection titled "Published images" stating that `ghcr.io/alexbomber12/sms-gateway-v2:latest` follows main and that immutable tags `sha-<short>` and `v*` are also available. Mention that the package needs to be made publicly readable in repo Settings → Packages once after the first publish (one-time manual operator step) so that `docker compose pull` works without authentication on a host that does not have a GHCR token configured.

## Tests

No code-level tests apply to a workflow file. Verification is operational:

1. Workflow file syntactically valid (GitHub will error in the Actions UI if not). The PR author runs `act` locally if available, but this is not a hard gate.
2. After merge, the Actions tab shows the workflow run completing successfully and a new package version appears under the repo's Packages tab.
3. From any host with docker, `docker pull ghcr.io/alexbomber12/sms-gateway-v2:latest` succeeds (after the one-time public-read setting).

These checks are part of the operator post-merge runbook, not the PR's automated CI.
