# PR-028: Heartbeat surfaces modem health and queue metrics

Branch: feat/pr-028-heartbeat-modem-health
- Type: feature
- Complexity: medium
- Depends on: PR-024
- Priority: 2
- Coder: codex

## Problem

Verified by reading `src/sms_gateway_v2/relay/heartbeat.py` and `src/sms_gateway_v2/relay/models.py`. The current heartbeat message reads `Status: running`, `Started: <iso>`, `Last SMS: <iso or (none)>`, `Last error: <str or (none)>`. It reflects only the FastAPI process being alive. Not reflected in the heartbeat: modem registration state, signal quality, operator, cellular registration (roaming or home), queue depths, SMS delete failure count, or time since last successful Telegram delivery.

Verified operationally: on 2026-06-11 the modem lost D-Bus path visibility due to USB re-enumeration. The relay processed heartbeat cycles for 5 days sending `Status: running` while zero SMS were being delivered. The operator had no signal that anything was wrong.

The operator confirmed the target detection latency at 24 hours (heartbeat cadence stays unchanged) and requested all seven candidate fields be surfaced.

## Scope

Extend RelayState with seven new fields, thread them from the sources that already collect the underlying data (watchdog, queue gauges, PR-024 delete-failure state, worker telegram result path), and update the heartbeat formatter to render them. When any field indicates degradation (modem not registered, or delete failures greater than zero, or last successful delivery older than a threshold), the heartbeat title changes to alert form.

Out of scope:
- New scheduler frequency (heartbeat stays at 24 hours per operator preference).
- New notification channel (Telegram bot remains the single channel).
- Automatic recovery actions triggered by heartbeat content.
- Changing the pydantic serialization convention for the `/state` endpoint.

## Implementation notes

### Step 1: Extend RelayState

Add fields to `RelayState` in `relay/models.py`:

```
modem_state: str | None = None
modem_signal_percent: int | None = None
modem_operator: str | None = None
modem_registration: str | None = None
queue_pending_count: int | None = None
queue_failed_count: int | None = None
last_telegram_success_at: datetime | None = None
```

The four modem fields are populated by the watchdog on each successful poll. `sms_delete_failures_count` and `last_delete_failure_at` are already added by PR-024. The two queue counts are populated by the queue gauge updater. `last_telegram_success_at` is set by the worker on successful send.

Keep existing fields unchanged (`status`, `started_at`, `last_sms_received_at`, `last_error`).

### Step 2: Wiring

- Watchdog: on each successful signal read and registration read, update `modem_state`, `modem_signal_percent`, `modem_operator`, `modem_registration` on the shared state. The watchdog already has this data in hand (it emits `signal_read` and `registration_read` logs).
- Queue gauges: the existing periodic queue scan already computes counts for pending and failed. Update `queue_pending_count` and `queue_failed_count` on state at the same time it updates the Prometheus gauges.
- Worker: on successful send (line where `sms_delivered_total` is incremented today), also set `last_telegram_success_at = datetime.now(UTC)` on state.

Use whatever mutation pattern the state currently uses (probably a helper method on Relay or a state container). If the state is presently frozen pydantic, replace it via a `model_copy(update={...})` call, matching existing convention.

### Step 3: Heartbeat body composition

Healthy state (no degradation reason true) title stays `SMS Gateway v2: alive`. Body:

```
Status: <status>
Started: <started_at>
Last SMS: <last_sms_received_at or "(none)">
Last error: <last_error or "(none)">

Modem: <modem_state>, signal <signal_percent>%, <operator> (<registration>)
Queue: pending <pending>, failed <failed>
Deletes failed: <sms_delete_failures_count>
Last Telegram OK: <last_telegram_success_at or "(none)">
```

Degraded state (any of): `modem_state != "registered"` OR `sms_delete_failures_count > 0` OR (`last_telegram_success_at is not None` AND `now - last_telegram_success_at > timedelta(hours=48)`).

Degraded title changes to `SMS Gateway v2: ALERT` and body prepends an ALERT block that lists which reasons triggered:

```
<b>ALERT</b>
Reasons:
- modem state: <modem_state> (expected registered)
- delete failures: <count>
- last successful delivery: <duration> ago

Status: <status>
...
```

Reasons list only fires that are currently true. Use bold HTML tags on the ALERT header and the "Reasons:" label to match existing Telegram HTML formatting mode from PR-005.

### Step 4: Duration formatting helper

Add `format_duration_since(timestamp: datetime | None) -> str` that returns `"5 days 2 hours"`, `"3 minutes 12 seconds"`, `"47 seconds"`, `"(none)"` for null. Round to two largest non-zero units. Place in `src/sms_gateway_v2/util/time_format.py` (new module).

### Step 5: Handling missing data gracefully

At container startup, before the watchdog has completed its first cycle, `modem_state` is None. The heartbeat may fire in this window if the operator configures a very short cadence. Handle gracefully: render as `"Modem: unknown"`. Do not treat unknown as degraded; a heartbeat that fires before the first watchdog cycle is a startup race and should not falsely alarm.

Similarly, if queue gauges have not run yet, render counts as `"unknown"`. If `last_telegram_success_at` is None (no successful delivery yet since restart), render as `"(none)"` and skip the age check.
