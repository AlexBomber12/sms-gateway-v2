# PR-020: Document AppArmor cache stale-skip workaround

Branch: docs/pr-020-apparmor-cache-reset
- Type: docs
- Complexity: low
- Depends on: none
- Priority: 5
- Coder: codex

## Problem

When the AppArmor profile `deploy/apparmor/sms-gateway-v2` is updated and reloaded with the documented command `sudo apparmor_parser -r -W /etc/apparmor.d/sms-gateway-v2`, the parser sometimes detects an unchanged compiled binary in `/var/cache/apparmor/<hash>/` and skips the actual policy reload in the kernel. The audit log shows this as:

```
apparmor="STATUS" operation="profile_replace"
  info="same as current profile, skipping"
  profile="unconfined" name="sms-gateway-v2"
```

The source file at `/etc/apparmor.d/sms-gateway-v2` reflects the new rules, but the kernel continues to enforce the prior compiled policy. New rules are NOT in effect. This was hit in production on 2026-05-10 while applying PR-019; the operator had to fall back to a force-reload sequence to make the new rules active:

```bash
sudo apparmor_parser -R /etc/apparmor.d/sms-gateway-v2
sudo rm -rf /var/cache/apparmor/*/sms-gateway-v2
sudo apparmor_parser -a -W /etc/apparmor.d/sms-gateway-v2
```

The current `docs/deploy.md` instructs only the simple `-r -W` reload and does not mention the cache-stale-skip case. The next operator who updates the profile (anyone applying a future PR-NN that touches AppArmor) will hit the same trap and waste time on diagnostics.

## Scope

Document the cache-stale-skip behavior and the force-reload fallback sequence in `docs/deploy.md`, in the existing AppArmor section. No code changes, no profile changes.

Out of scope: changing the install procedure for first-time setup (the simple `-r -W` works for fresh loads), preventing the cache-stale-skip itself (that would require an upstream apparmor_parser fix).

## Files to modify

- `docs/deploy.md`

## Implementation notes

In the AppArmor section of `docs/deploy.md`, after the existing `apparmor_parser -r -W` install command and before the `aa-status` verification step, add a short note plus a fenced bash block with the force-reload sequence.

Suggested wording (the implementer can adapt; keep it concise and operator-focused):

> If `dmesg` shows `apparmor="STATUS" ... info="same as current profile, skipping"` after a profile update and the new rules do not appear to take effect (for example, expected DENIED entries still fire), the parser detected an unchanged compiled cache and skipped the kernel reload. Force a clean reload:
>
> ```bash
> sudo apparmor_parser -R /etc/apparmor.d/sms-gateway-v2
> sudo rm -rf /var/cache/apparmor/*/sms-gateway-v2
> sudo apparmor_parser -a -W /etc/apparmor.d/sms-gateway-v2
> sudo aa-status | grep sms-gateway-v2
> ```
>
> The window between `-R` (remove) and `-a` (add) is approximately one second. Existing container processes retain their loaded profile through the gap; do not run `docker compose up -d --force-recreate` until `aa-status` confirms the profile is loaded again.

Place this addition inside the existing AppArmor section. Do not introduce a new top-level heading; the cache-skip case is a sub-condition of the existing reload procedure, not a separate workflow.

Do NOT remove or modify the existing `apparmor_parser -r -W` instruction. The simple form remains the default; the force-reload is a fallback for the documented edge case.
