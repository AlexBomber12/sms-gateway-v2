# PR-006: Modem watchdog with active reset on stuck states

Branch: pr-006-modem-watchdog
- Type: feature
- Complexity: medium
- Depends on: PR-001
- Priority: 2
- Coder: any

## Problem

The `modem_signal_percent` and `modem_state` Prometheus gauges exist on `MetricsRegistry` but nothing populates them. Worse, when an MTS SIM in roaming on Italian networks loses signal or gets stuck in `searching`/`denied` for an extended period, the relay receives no SMS but does nothing about it — the operator only finds out when they check `mmcli -m 0` manually. The legacy gammu setup relied on a bash watchdog that called `mmcli --reset` after a fixed timeout; we need the same recovery logic in the new architecture.

A periodic `ModemWatchdog` task that polls signal and registration state every 60s, updates the gauges, and resets the modem after a configurable threshold of consecutive zero-signal polls or stuck bad states is the right shape.

## Scope

Add a `ModemWatchdog` class that polls the modem on a fixed interval, updates `modem_signal_percent` and `modem_state` gauges, and calls `modem_client.reset()` when the modem appears stuck. Add a new `reset()` method on `ModemManagerClient` that calls D-Bus `Modem.Reset()`. Wire the watchdog into the FastAPI lifespan alongside the gauge updater and cleanup scheduler.

Out of scope: dead-man heartbeat to Telegram (PR-007), restart of the systemd-managed `ModemManager` service itself (mmcli has no API for this; would require host-level escalation), automatic SIM PIN unlock (the EC25-EUX SIM is not PIN-locked in our setup).

## Files to modify

`src/sms_gateway_v2/modem/client.py`:
- Add `async def reset(self) -> None` that calls the `Reset` method on the `org.freedesktop.ModemManager1.Modem` interface for the cached modem path. Wraps D-Bus errors as `ModemManagerUnavailable` consistent with other operations. Logs `modem_reset_called` with `modem_path`. The watch_added callbacks are cleared by ModemManager too, so set `_added_watch_resubscribe_required = True` so the next `connect()` or first operation re-subscribes them.

`src/sms_gateway_v2/relay/watchdog.py` (new):
- `class ModemWatchdog` with `__init__(modem_client, metrics, interval_seconds, signal_zero_threshold, bad_state_minutes)`.
- Internal state: `_consecutive_zero_signal_polls: int = 0`, `_bad_state_since: datetime | None = None`, `_stop_event: asyncio.Event`.
- `async def run(self) -> None`: same `wait_for + suppress(TimeoutError)` loop pattern as the other periodic tasks. Each iteration calls `_poll_once()`.
- `async def _poll_once(self) -> None`:
  - Try `signal = await self._modem_client.get_signal_quality()` and `state = await self._modem_client.get_registration_state()`. On `ModemError` subclasses, log `watchdog_poll_failed` and return; do not count this toward thresholds (the modem might just be temporarily busy).
  - Update `modem_signal_percent.set(signal.percent)`. Reset all `modem_state.labels(state=...)` to 0 except the current one set to 1 (drives a single-active-state gauge series).
  - Increment `_consecutive_zero_signal_polls` if `signal.percent == 0`, else reset to 0.
  - If `state in {RegistrationState.DENIED, RegistrationState.SEARCHING, RegistrationState.UNKNOWN}`, set `_bad_state_since` if not already set; else clear it.
  - Reset condition: `_consecutive_zero_signal_polls >= self._signal_zero_threshold` OR (`_bad_state_since is not None` AND `now - _bad_state_since >= timedelta(minutes=self._bad_state_minutes)`). On reset: log `watchdog_triggering_modem_reset` with reason, call `await self._modem_client.reset()`, increment `metrics.modem_resets_total`, clear both counters.
- `def stop(self) -> None`: sets the stop event.

## Implementation notes

The `modem_state` gauge has a `state` label so each registration state is its own time series. To make Prometheus see the "current" state as 1 and others as 0, the watchdog must explicitly `.set(0)` for all known states except the current one. Iterate over all `RegistrationState` enum values, set the current one to 1, all others to 0. This avoids stale `1` values on previous states.

ModemManager's `Modem.Reset` method is asynchronous on the modem hardware side — it returns immediately but the modem actually disappears from D-Bus for several seconds before reappearing as a new object path. The next operation on `ModemManagerClient` will re-discover via `find_modem()`. Don't try to wait for the modem to come back inside `reset()`; just clear the cache and let the normal flow handle it.

Polling frequency: 60s is intentional. The MTS SIM in roaming gets ~1-2 SMS per month per the project context; a watchdog tick every 60s is rarely-triggered overhead, well below noise floor. Setting the floor at 10s prevents foot-guns.

The reset thresholds (5 consecutive zero-signal polls, 10 minutes in bad state) translate to ~5 minutes of zero signal before reset. Aggressive enough to recover from transient cell tower issues, conservative enough to avoid resetting during normal handover delays in roaming.

## Success criteria

1. `scripts/ci.sh` exits 0.
2. `modem_signal_percent` and `modem_state{state="..."}` gauges show real values when the watchdog is running.
3. Five consecutive zero-signal polls trigger `modem_client.reset()` and increment `modem_resets_total` by 1.
4. After reset, the next `find_modem()` call re-discovers the modem path and added-watch subscriptions are restored.
5. A poll failure does not crash the watchdog loop.
6. Lifespan shutdown stops the watchdog before stopping the relay.
