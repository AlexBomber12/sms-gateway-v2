# PR-026: Distinguish permanent from transient failures in queue requeue

Branch: fix/pr-026-queue-permanently-failed-flag
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 2
- Coder: codex

## Problem

Verified by reading `src/sms_gateway_v2/queue/queue.py` line 296 to 342 (`requeue_failed`) and `src/sms_gateway_v2/worker/worker.py` line 91 to 133 (delivery failure branches). The `requeue_failed` cleanup task, invoked once per hour by `cleanup_scheduler`, moves every item from `failed/` back to `pending/` if `first_seen_at >= (now - max_age_days)` (default 30 days).

The predicate does not distinguish between permanent failures and transient ones:

- `TelegramAuthError` (worker.py line 91 to 94) is permanent: the bot token has been revoked or is invalid. Retrying at hourly cadence will fail identically every time.
- `delivery_failed_permanent reason="exhausted"` (worker.py line 168 to 176) is permanent: the retry schedule was exhausted (7 attempts across 24 hours). Retrying an hour later is not going to succeed where 7 attempts failed.
- `TelegramTransportError` (worker.py line 108 to 133) is transient: network blips are worth retrying.

Under the current logic, an `auth_error` item is requeued every hour for 30 days, generating 720 Telegram API calls and 720 mark_failed transitions per item, all guaranteed to fail. Multiple failed items compound this cost. In an operational scenario where token rotation was missed for a week, this generates 168 spurious API calls per queued SMS.

## Scope

Introduce a `permanently_failed: bool` flag on QueueItem. Worker sets it to True when marking failed due to `auth_error` or `exhausted`. `requeue_failed` skips any item with the flag set. Transient failures (`transport_error`) continue to be requeued as today.

Out of scope:
- Cleanup policy for permanently_failed items. They remain in `failed/` until `cleanup_failed` moves them out based on age (`queue_max_age_days`). This preserves the existing max-age behavior.
- Retroactive migration of existing failed items. Any item currently in `failed/` predates this PR and lacks the flag; it will parse as False (transient) and be requeued once, fail, then mark_failed with the flag set. This is a one-time correction cost.
- Manual retry mechanism for permanently_failed items. If an operator rotates the token and wants old failed items requeued, they move them by hand from `failed/` to `pending/` after clearing the flag in the JSON. Documented in the PR description, not in a UI.

## Implementation notes

### Step 1: Extend QueueItem model

In `queue/models.py`, add:

```
permanently_failed: bool = False
```

Placement: after `attempts` and `last_attempt_at`. Default False preserves backwards compatibility for items already persisted in the queue.

### Step 2: Worker sets the flag when marking failed permanently

In `worker.py`, at each `mark_failed` site:

- `TelegramAuthError` branch (currently around line 91 to 94): use `mark_failed(item, permanently_failed=True)`.
- `delivery_failed_permanent reason="exhausted"` branch (currently around line 168 to 176): use `mark_failed(item, permanently_failed=True)`.
- Any other branch that reaches `mark_failed` for retryable failure (bare exception handler around line 121 to 133 for unexpected `Exception`): use the current `mark_failed(item)` call, which implies `permanently_failed=False` via default.

Add a helper on `Queue`: `mark_failed(item, permanently_failed: bool = False)` that persists the flag into the JSON on disk before the atomic_move to `failed/`.

### Step 3: requeue_failed skips permanently_failed items

In `queue.py` around line 325, before the existing `first_seen_at >= cutoff` check:

```
if item.permanently_failed:
    continue
```

Emit `queue_failed_item_skipped_permanent` (info) with fields `item_id`, `path`, so an operator can see in logs which items are being intentionally skipped.

### Step 4: Log naming

- `queue_failed_item_skipped_permanent` (info): new. Fields as above.
- Existing `queue_failed_requeued` count log remains and counts only actually-requeued items.

## Tests

1. `test_queue_item_defaults_permanently_failed_to_false`: unit test on model.

2. `test_worker_marks_auth_error_as_permanently_failed`: simulate `TelegramAuthError`. Verify `mark_failed` called with `permanently_failed=True`. Verify persisted JSON on disk includes `"permanently_failed": true`.

3. `test_worker_marks_exhausted_as_permanently_failed`: simulate `retry_schedule` exhaustion. Verify same as above.

4. `test_worker_marks_transport_error_as_transient`: simulate `TelegramTransportError` within retry budget. Item is not immediately marked failed; when retry budget exhausts, it becomes `permanently_failed=True`. Test both mid-retry state and final state.

5. `test_worker_marks_unexpected_exception_as_transient`: bare Exception is caught. `mark_failed` called with default `permanently_failed=False`.

6. `test_requeue_failed_skips_permanent_items`: two items in failed dir, one with flag True and one with flag False. Both within cutoff. Only the False item is moved. `queue_failed_item_skipped_permanent` logged for the True item.

7. `test_requeue_failed_still_moves_transient_items`: regression test that existing behavior for transient failures is preserved.

8. `test_requeue_failed_backward_compat_with_missing_flag`: a JSON file on disk with no `permanently_failed` field (simulating pre-PR state). Item parses with default False and is requeued as before.

## Success criteria

- `QueueItem` has `permanently_failed: bool` field with default False.
- Worker sets the flag to True on `TelegramAuthError` and on retry-schedule exhaustion.
- Worker leaves the flag False on transient failures (`TelegramTransportError`, bare `Exception`).
- `Queue.mark_failed` accepts `permanently_failed` parameter and persists it.
- `requeue_failed` skips items with the flag set, emits `queue_failed_item_skipped_permanent` log.
- Existing items without the flag parse as False and are requeued once (transient interpretation).
- All eight tests pass. Existing queue and worker tests continue to pass unmodified.
- `scripts/ci.sh` exits 0 with 100 percent coverage on modified modules.
- PR description references the analysis: 720 spurious API calls per stuck auth_error item over 30 days, the code paths in worker.py and queue.py, and the manual recovery procedure for operators who want to reactivate permanently_failed items after token rotation.
- No changes to modem client, watchdog, relay, cleanup scheduler policy, heartbeat, docs, or deploy artifacts.
