# PR-007: Dead-man heartbeat to Telegram

Branch: pr-007-dead-man-heartbeat
- Type: feature
- Complexity: low
- Depends on: PR-001
- Priority: 3
- Coder: any

## Problem

Even with `/healthz`, `/state`, `/metrics`, and the modem watchdog from PR-006, there is one failure mode none of them catch: the entire NAS or container is dead. If the host loses power, crashes, or gets rebooted into a broken state, the relay just stops existing and no SMS gets forwarded. The operator finds out only when they happen to look at Grafana — or when they realize a critical bank SMS never arrived.

A periodic "I am alive" heartbeat to Telegram closes this gap. At a configured interval (default 24 hours), the relay sends a brief status message to the same `TELEGRAM_CHAT_ID` it uses for SMS forwards. If the operator does not see the heartbeat for >24 hours, the service is dead and they investigate. This is the simplest, most reliable dead-man pattern; it requires no external monitoring service.

## Scope

Add a `HeartbeatScheduler` class that periodically sends a Telegram message containing the relay's current state (status, started_at, last_sms_received_at, last_error). Wire into the FastAPI lifespan. The heartbeat reuses the same `TelegramClient` and chat as SMS forwarding by default; an optional separate chat can be configured for operators who want to keep heartbeats out of the main SMS channel.

Out of scope: heartbeats to non-Telegram targets (healthchecks.io, Pushover), structured pager-style escalation, dynamic interval tuning.

## Implementation notes

The 86400s default (24 hours) is the right tradeoff for a 1-2 SMS/month service. Shorter intervals (1 hour) would create more noise than signal in the operator's chat. For testing, set `HEARTBEAT_INTERVAL_SECONDS=60` and watch.

Sending the first heartbeat AFTER the first interval (not immediately at startup) avoids two annoying edge cases: a noisy heartbeat on every container restart during deployment iteration, and a heartbeat from a relay that crashes 5s into startup. If the relay survives the first interval, it is in a meaningfully steady state.

The fallback chain `heartbeat_telegram_chat_id or telegram_chat_id` is intentional — most operators will use the same chat. The separate setting exists for operators who maintain a dedicated `infra-alerts` Telegram channel.

The heartbeat message uses `TelegramMessage(...)` constructor directly rather than `from_sms`. The `from_sms` helper is for actual SMS forwarding with HTML-escaped phone-number-and-text shape; heartbeats have a different format.

A heartbeat send failure is logged but never raises. If Telegram is down, the next heartbeat will succeed (or also fail, in which case the relay is doing all it can do — the operator notices missing heartbeats and investigates).

## Success criteria

1. `scripts/ci.sh` exits 0.
2. With `HEARTBEAT_ENABLED=true` and the relay running, a Telegram message is sent every `HEARTBEAT_INTERVAL_SECONDS` seconds containing the current relay status.
3. With `HEARTBEAT_ENABLED=false`, no heartbeat task is spawned in the lifespan.
4. A `TelegramError` during heartbeat send is logged but does not crash the loop.
5. The first heartbeat fires after one full interval, not immediately at startup.
