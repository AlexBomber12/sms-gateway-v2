# PR-015: Document Telegram bot token rotation procedure

Branch: docs/pr-015-token-rotation-runbook
- Type: docs
- Complexity: low
- Depends on: none
- Priority: 5

## Problem

The Telegram bot token currently used in production was leaked into the chat transcript during the cutover diagnostics on 2026-05-09. The token grants full control of the bot: ability to send arbitrary messages to the chat, read messages forwarded to the bot, and (depending on bot settings) participate in groups the bot is in. Anyone with the token can impersonate the bot.

There is no documented procedure in this repo for rotating the token. Operators (current and future) need a step-by-step runbook that captures:

1. How to revoke the current token via @BotFather.
2. How to obtain the new token without exposing it in shell history or chat windows.
3. How to update `deploy/.env` on the production host atomically.
4. How to restart the container without losing in-flight queue items.
5. How to verify that the new token works before declaring rotation complete.

The runbook also serves as the template for any future credential rotation (chat ID change, bot replacement, additional bot for multi-recipient delivery).

## Scope

Add a documentation file `docs/runbooks/rotate-telegram-token.md` (or similar) that captures the rotation procedure end-to-end. Reference it from `docs/deploy.md` and from the project README.

Out of scope: automating the rotation, integrating with a secrets management system (Vault, sops, age), or any code change to how the application reads the token. The application already reads the token via env via pydantic-settings; that path is correct and does not need touching.

## Implementation notes

Runbook structure. Use the following section headers in order:

1. `When to rotate`. Trigger conditions: token leak (chat, screenshot, screen share), employee offboarding (not applicable solo, but mention for completeness), routine schedule (annually or on each major release).
2. `Prerequisites`. SSH access to the host running the container, ability to chat with @BotFather on Telegram, the chat ID `136565198` (or refer to the operator's own chat ID as documented in `deploy/.env`).
3. `Procedure`. Numbered steps:
   - Open a chat with @BotFather, send `/mybots`, select the bot used by sms-gateway-v2, choose `API Token`, then `Revoke current token`. Confirm. BotFather replies with the new token.
   - Copy the new token. Do NOT paste it into chat windows, terminal commands, or any logged surface. Use the system clipboard.
   - On the host, `cd ~/repos/sms-gateway-v2/deploy`. Edit `.env` (the file already has `chmod 600` and is `.gitignore`-d; verify with `ls -la .env`). Replace the `TELEGRAM_BOT_TOKEN=...` value with the new token. Save and close.
   - Verify the env file: `grep TELEGRAM_BOT_TOKEN .env | head -c 30 && echo` (prints first 30 chars only — confirms shape without dumping the full value).
   - Restart the container: `docker compose -p sms-gateway-v2 up -d --force-recreate`.
   - Watch logs for the first heartbeat or the next SMS: `docker compose -p sms-gateway-v2 logs --tail=20 -f`. A `telegram_send_success status_code=200` event confirms the new token works.
   - Verify in the Telegram chat that the bot's next message appears. The first heartbeat may not arrive for up to 24 hours per `HEARTBEAT_INTERVAL_SECONDS`; for an immediate test, send any SMS to the modem.
4. `Rollback`. If the new token fails (`telegram_send_failed` events with 401 Unauthorized), the old token is revoked and gone. The procedure to recover is to immediately generate a brand-new token via the same BotFather flow (revoke + receive yields a new token even if you just rotated). There is no way to "go back" to the prior token.
5. `Cleanup`. After 24 hours of stable operation, search the operator's chat history and any external systems (Slack, email drafts) for the old token string and purge any traces. Note that revoked tokens are dead by Telegram's side; cleanup is for hygiene, not security.

The runbook MUST NOT include an example token string anywhere, even an obviously-fake one. The example commands MUST use the literal placeholder `<NEW_TOKEN>` so a copy-paste cannot accidentally introduce a fake token into production.
