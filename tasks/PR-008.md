# PR-008: Production cutover from AI-Server gammu relay

Branch: pr-008-production-cutover
- Type: docs
- Complexity: low
- Depends on: PR-005, PR-006
- Priority: 4
- Coder: any

## Problem

The legacy SMS gateway runs on AI-Server (192.168.50.4) using gammu + a bash watchdog with a Huawei E353 modem. It must keep running until the new sms-gateway-v2 is verified on the NAS (192.168.50.2) with the Quectel EC25-EUX dongle. The cutover is a one-time procedure that needs to be documented in a single place so it can be followed without re-deriving the steps. Without a runbook, the operator will hesitate during the cutover window and risk a longer SMS outage than necessary.

There is also a one-time data concern: gammu's inbox database contains hashes of recently-received SMS that the new dedup database does not know about. If a message physically present on the SIM at cutover time was already forwarded by the old relay, the new relay will forward it again. A small import script that pre-populates the new SQLite dedup table with hashes from the gammu inbox closes this window.

## Scope

Add `docs/migration-from-v1.md` with a step-by-step cutover runbook: pre-flight checks, modem swap, container start, smoke test, fallback procedure if v2 misbehaves. Add `scripts/import-gammu-dedup.py` as a one-time tool that reads gammu's inbox SQLite/MySQL db (or the dump file) and inserts content hashes into the v2 `dedup.db`.

Out of scope: live SMS replay from gammu archives (the dedup window is short — a few minutes at cutover — so historical messages are not a concern), automated rollback, dual-write mode running both relays simultaneously.

  - Send a test SMS to the SIM from a second phone. Confirm it arrives in Telegram within 30s.
- Section "Post-cutover":
  - Leave the legacy AI-Server service stopped but installed for one week as a fallback.
  - Configure Prometheus to scrape `http://192.168.50.2:8091/metrics` and add an alert: `last_sms_received_seconds` older than 7 days WITHOUT any heartbeat is suspicious (depends on PR-007).
  - After one week of clean operation, decommission the legacy relay: uninstall gammu service, remove cron, document in homelab notes.
- Section "Fallback" (if v2 misbehaves in the first hour):
  - Stop v2 container: `docker compose -f deploy/docker-compose.yml down`.
  - Move SIM back to Huawei E353 on AI-Server.
  - Start legacy service: `ssh ai-server "sudo systemctl start sms-gateway-v1"`.
  - File a bug in this repo with the v2 logs attached.

`scripts/import-gammu-dedup.py` (new):
- Standalone Python script invoked as `python scripts/import-gammu-dedup.py --gammu-db /path/to/gammu/inbox --target-db ./state/dedup.db`.
- Reads the gammu inbox table (column names depend on gammu's schema; typical fields are `Number`, `TextDecoded`, `ReceivingDateTime`).
- For each row, computes the content hash using the SAME formula as `Queue._content_hash` (number | text | minute-bucket ISO timestamp). Important: the script must produce identical hashes to the running relay or the dedup is useless.
- Inserts each hash into `seen_messages` with `status='sent'` and `last_status_at=time.time()` so cleanup will eventually purge them per `QUEUE_SENT_RETENTION_DAYS`.
- Idempotent: handles duplicate-hash inserts as no-ops.
- Prints a summary: rows read, hashes inserted, duplicates skipped.
- Self-contained: imports `aiosqlite` and `hashlib`. Does NOT import from `sms_gateway_v2` to keep the script runnable without installing the package.

## Implementation notes

The gammu schema varies by installation. Some setups use SQLite (`gammu-smsd-inject` files), others MySQL. Document in the script's docstring that it expects SQLite by default and offer a `--gammu-mysql-dsn` flag as a future extension. For the actual cutover, the user can provide a CSV dump if the schema differs — the script's main loop is just "for each (number, text, timestamp), compute hash, insert".

The hash formula is duplicated (script vs `Queue._content_hash`). This is deliberate: making the script depend on the package would require installing `sms_gateway_v2` somewhere with all its runtime deps just to run a one-shot import. The duplication is small (~5 lines) and the formula is stable per the dedup contract. Leave a comment in both places noting the duplication so a future change to the hash bucket logic updates both.

The runbook commits to Telegram-as-test-channel for the smoke test. If the operator wants to use a separate test chat for the cutover and only switch to the production chat afterward, document that as an alternative — set `TELEGRAM_CHAT_ID` to a test chat, do the smoke test, then switch and `docker compose restart`.
