## Problem

The repo ships placeholder `Dockerfile` and `deploy/docker-compose.yml` files (literally `# TODO: filled in sprint 5`). The service cannot be deployed to the NAS until these are real. The container needs:

1. A multi-stage build that produces a minimal runtime image.
2. A non-root user (uid 1000) for the app.
3. Access to the host system D-Bus socket so `dbus-fast` can talk to `ModemManager`.
4. A bind volume for `state/` so the durable queue and dedup database survive container restarts.
5. Published port 8091 bound to `127.0.0.1` only (LAN-trust model, no external exposure).

Image registry per project convention: `ghcr.io/alexbomber12/sms-gateway-v2`.

The compose file describes the production deployment on NAS at `192.168.50.2` running Ubuntu 24.04 with `ModemManager` on the host.

## Scope

Replace the placeholder `Dockerfile` and `deploy/docker-compose.yml` with real, production-ready versions. Add a `.dockerignore` to keep build context lean. Add `docs/deploy.md` documenting the polkit configuration that lets the container's user talk to ModemManager over the system bus, the volume mount layout, and the health check.

Out of scope: GitHub Actions workflow that publishes the image (separate infra PR if needed), systemd unit file (compose with `restart: unless-stopped` is sufficient), Kubernetes manifests.

## Implementation notes

D-Bus access from inside a container is the only non-trivial piece. The bind mount of `/var/run/dbus/system_bus_socket` is the standard pattern; what is less standard is that ModemManager's polkit policy gates most operations behind a uid check, and the container's uid 1000 is a different "user" from the host's uid 1000 from polkit's perspective. The polkit rule in `docs/deploy.md` matches by uid, which is the simplest reliable approach for a single-tenant home setup. Document this clearly so the user knows what trust they are granting.

The `:ro` mount flag on the D-Bus socket is intentional — `dbus-fast` only reads and writes via D-Bus message protocol, not via the socket file directly. The socket itself is a Unix socket; the `:ro` is on the bind mount path, not the bus operations.

`HEALTHCHECK` uses `curl`. Some `python:3.12-slim` images ship without `curl`. If that is the case, add `RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*` to the runtime stage. Verify before merging.

The named volume `sms-gateway-state` keeps queue data in a Docker-managed location (`/var/lib/docker/volumes/...`). If the user prefers a host bind mount under `/srv/sms-gateway-v2/state`, that is also acceptable — note it as an alternative in `docs/deploy.md`.

## Success criteria

1. `docker build -t sms-gateway-v2:test .` succeeds.
2. `docker run --rm -e RELAY_ENABLED=false -p 127.0.0.1:8091:8091 sms-gateway-v2:test` starts and `curl http://127.0.0.1:8091/healthz` returns 200.
3. The runtime image runs as uid 1000, not root (`docker run --rm sms-gateway-v2:test id` reports uid 1000).
4. `docker compose -f deploy/docker-compose.yml config` validates without errors.
5. `docs/deploy.md` documents the polkit rule, volume layout, and verification steps end-to-end.
6. `scripts/ci.sh` still exits 0 (no Python source changes needed; if any tests reference `Dockerfile` text they should be updated).
