# PR-023: Close modem reset blind window with immediate re-subscribe

Branch: fix/pr-023-modem-reset-immediate-resubscribe
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 1
- Coder: codex

## Problem

Verified by reading `src/sms_gateway_v2/modem/client.py` at lines 382 to 406. After a successful `call_reset()` the client executes three steps:

1. `self._modem_path = None`
2. `self._unsubscribe_all_added_watchers()`
3. `self._added_watch_resubscribe_required = bool(self._added_callbacks)`

Re-subscription of MessageAdded watchers is deferred to the next call into `_ensure_modem_path()` (client.py lines 670 to 677). That next call happens in the next watchdog poll cycle, which is bounded by `modem_watchdog_interval_seconds` (default 60).

Between the return of `reset()` and the next watchdog poll there is a window of 0 to 60 seconds during which the modem may have completed its reset (typical duration 5 to 30 seconds on EC25 hardware), re-registered on the network, and received an SMS. `MessageAdded` signal for that SMS is never delivered to the relay because no handler is subscribed. The SMS lands in EC25 storage and is only discovered on the next container restart via `_drain_existing_messages`.

This is a silent SMS loss window that opens every time the watchdog decides to reset the modem.

## Scope

Extend `reset()` to actively wait for the modem to reappear after `call_reset()` and re-subscribe MessageAdded watchers before returning. The waiting is bounded and instrumented so an operator can see the recovery timing in logs.

Out of scope:
- Changing when the watchdog decides to reset. That policy is separate.
- Subscribing to Manager-level InterfacesAdded signals for hotplug detection.
- Modifying the watchdog code path.
- Changing `_drain_existing_messages` behavior; it remains the backstop for any SMS that arrived while the client had no path at all.

## Files to modify

- `src/sms_gateway_v2/modem/client.py`
- `src/sms_gateway_v2/config.py` (one new setting for the reset-wait bound)
- `tests/test_modem/test_client.py` or the file that currently exercises `reset()`

## Implementation notes

### Step 1: New configuration setting

Add to `Settings` in `config.py`:

```
modem_reset_reappear_timeout_seconds: float = Field(
    default=45.0,
    ge=5.0,
    le=180.0,
)
```

45 seconds covers the observed 5 to 30 second reset duration on EC25 with a safety margin. The bound is configurable so operators on different hardware can tune it. The setting is threaded into `ModemManagerClient` via the existing factory.

### Step 2: Add a bounded wait loop inside reset

After the existing `call_reset()` succeeds and after `self._unsubscribe_all_added_watchers()`, add a wait loop that polls `find_modem()` every 2 seconds up to `modem_reset_reappear_timeout_seconds` total. As soon as `find_modem()` succeeds:

1. `self._added_watch_resubscribe_required` is already true; call `_subscribe_missing_added_watchers(self._modem_path)` explicitly here so the subscription is in place before returning.
2. Emit `modem_reset_reappeared` (info) with fields `modem_path`, `wait_seconds`.
3. Return from `reset()`.

If the timeout expires without the modem reappearing, emit `modem_reset_reappear_timeout` (warning) with fields `wait_seconds` and let control return to the caller. `self._modem_path` remains None so the watchdog will retry on its next cycle, matching current behavior for the persistent absent-modem case. This preserves the existing recovery flow for the case where reset does not bring the modem back.

The 2 second poll interval is a private module-level constant `_RESET_REAPPEAR_POLL_INTERVAL_SECONDS = 2.0`. Do not expose it as a setting.

### Step 3: Instrumentation

Keep the existing `modem_reset_called` (info) log at the same location and shape. Add:

- `modem_reset_reappeared` (info): `modem_path`, `wait_seconds`
- `modem_reset_reappear_timeout` (warning): `wait_seconds`

Do not add new metrics in this PR.

### Behavioral invariants

- The reset method still returns on success once `call_reset` has been issued; the wait for reappear is bounded and never blocks indefinitely.
- If added-callback set is empty (no incoming subscribers), skip the wait and return immediately after unsubscribe. The wait exists only to close the subscription gap.
- `_added_watch_resubscribe_required` remains true on timeout so a later `_ensure_modem_path()` call still attempts subscription.

## Tests

1. `test_reset_waits_for_modem_reappear_and_resubscribes`: mock `call_reset` returning success, mock `find_modem` returning `ModemNotFound` twice then a fresh path. Verify total wait time approximately 4 seconds (two failed polls at 2 second interval), `_added_watch_keys` populated for new path when reset returns, `modem_reset_reappeared` log emitted.

2. `test_reset_returns_on_reappear_timeout_without_raising`: mock `find_modem` always raises `ModemNotFound`. Reset must return normally, emit `modem_reset_reappear_timeout`, leave `_modem_path` as None, leave `_added_watch_resubscribe_required` as True.

3. `test_reset_skips_wait_when_no_added_callbacks`: no added callbacks registered. Reset should not call `find_modem` at all in its wait loop. Total elapsed time inside reset well under 1 second.

4. `test_reset_reappear_wait_bounded_by_setting`: parameterize `modem_reset_reappear_timeout_seconds=6.0` and mock `find_modem` always failing. Assert total wait approximately 6 seconds, not longer.

5. `test_reset_still_emits_modem_reset_called`: regression test that the existing log event is preserved with the same fields.
