# PR-003: Periodic cleanup scheduler for queue retention

Branch: pr-003-cleanup-scheduler
- Type: feature
- Complexity: low
- Depends on: PR-001
- Priority: 3
- Coder: any

## Problem

`Queue.cleanup_sent`, `Queue.cleanup_failed`, and `Queue.requeue_failed` exist from sprint 3 but are never invoked. Files in `state/sent/` and `state/failed/` accumulate forever; SMS messages that hit `failed/` after exhausting retries never get a second chance even if the underlying problem (Telegram outage, network) was transient. Over months on a NAS this leaks disk space and silently drops recoverable messages.

A periodic task that calls all three retention methods at a configurable interval solves this without touching `Queue` itself. Default interval 1 hour is enough — these are housekeeping operations that are safe to run lazily.

## Scope

Add a `CleanupScheduler` class that periodically calls `queue.requeue_failed()`, `queue.cleanup_sent()`, and `queue.cleanup_failed()` using retention values from settings. Wire into the FastAPI lifespan alongside the gauge updater (PR-002).

Out of scope: per-method scheduling (all three run on the same tick), backoff for transient errors during cleanup (Queue methods already log and continue).

## Files to modify

`src/sms_gateway_v2/relay/cleanup_scheduler.py` (new):
- `class CleanupScheduler` with `__init__(queue, sent_retention_days, failed_retention_days, interval_seconds)`.
- `_stop_event: asyncio.Event`.
- `async def run(self) -> None`: loop until stop event. Each iteration calls `_run_cleanup()`, then sleeps until next interval via the same `wait_for + suppress(TimeoutError)` pattern as `QueueGaugeUpdater`.
- `async def _run_cleanup(self) -> None`: in order, `await self._queue.requeue_failed(max_age_days=self._failed_retention_days)`, `await self._queue.cleanup_sent(max_age_days=self._sent_retention_days)`, `await self._queue.cleanup_failed(max_age_days=self._failed_retention_days)`. Log each step's count. Wrap the body in `try/except Exception` and log `cleanup_iteration_failed` so a single failure does not kill the loop.
- `def stop(self) -> None`: sets the stop event.

`src/sms_gateway_v2/relay/factory.py`:
- Change return type to `tuple[SmsRelay, QueueGaugeUpdater, CleanupScheduler]`. Build the scheduler with `sent_retention_days=settings.queue_sent_retention_days`, `failed_retention_days=settings.queue_failed_retention_days`, `interval_seconds=settings.cleanup_interval_seconds`.

`src/sms_gateway_v2/app.py`:
- Lifespan startup: spawn `cleanup_task = asyncio.create_task(cleanup_scheduler.run())` after the gauge task. Store on `app.state.cleanup_task`.
- Lifespan shutdown: stop and await the cleanup task between gauge updater stop and `relay.stop()`. Same 2.0s timeout-then-cancel pattern.

`src/sms_gateway_v2/config.py`:
- Add `cleanup_interval_seconds: float = Field(default=3600.0, ge=60.0)`.

`.env.example`:
- Add `CLEANUP_INTERVAL_SECONDS=3600`.

`tests/test_relay/test_cleanup_scheduler.py` (new):
- `_run_cleanup` calls all three queue methods in order with correct retention values.
- `run` loops until `stop`: patch `asyncio.wait_for` to set the stop event after one iteration.
- `_run_cleanup` swallows exceptions: monkeypatch `queue.cleanup_sent` to raise; the loop logs and continues.

`tests/test_app_lifespan.py`:
- Extend enabled-lifespan test: cleanup scheduler is started after gauge updater and stopped before relay.

## Implementation notes

Order matters in `_run_cleanup`. `requeue_failed` runs first because it moves still-retriable items from `failed/` back to `pending/`. `cleanup_sent` and `cleanup_failed` run after so they only delete genuinely terminal files. Reverse order would let `cleanup_failed` delete an item that `requeue_failed` would have salvaged.

The minimum interval of 60s is not tight — typical operations take milliseconds. The floor exists to prevent foot-guns from operators setting `CLEANUP_INTERVAL_SECONDS=1` and pinning the SQLite WAL.

`requeue_failed(max_age_days=...)` uses the same retention as `cleanup_failed` intentionally. An item older than the retention window should be cleaned up, not requeued. Younger items get one more retry pass per cleanup tick.

## Success criteria

1. `scripts/ci.sh` exits 0.
2. The scheduler calls `requeue_failed`, `cleanup_sent`, and `cleanup_failed` once per `CLEANUP_INTERVAL_SECONDS` interval.
3. A failure in one cleanup call does not stop subsequent calls or kill the loop.
4. Lifespan shutdown order is: gauge updater stop, cleanup scheduler stop, relay stop.
