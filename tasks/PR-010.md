# PR-010: Deploy AppArmor unconfined for D-Bus access from container

Branch: fix/pr-010-apparmor-unconfined
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 1
- Coder: codex

## Problem

When the production compose stack from `deploy/docker-compose.yml` is started on an Ubuntu 24.04 host (NAS, 192.168.50.2) the FastAPI app fails on startup with the following exception during `relay.start()`:

```
dbus_fast.errors.DBusError: An AppArmor policy prevents this sender
from sending this message to this recipient; type="method_call",
sender="(null)" (inactive) interface="org.freedesktop.DBus.Introspectable"
member="Introspect" error name="(unset)" requested_reply="0"
destination="org.freedesktop.DBus" (bus)
```

The error is reproducible without any application code by running an in-container python script that connects to `org.freedesktop.DBus` via `dbus_fast.aio.MessageBus(BusType.SYSTEM)` and calls `bus.introspect("org.freedesktop.ModemManager1", "/org/freedesktop/ModemManager1")`. The same call from the host shell as `alexey` (uid 1000) succeeds via `mmcli`.

Adding `--security-opt apparmor=unconfined` to the docker invocation makes the introspection succeed.

Root cause: Docker on Ubuntu applies the `docker-default` AppArmor profile to every container. That profile does not grant rules permitting D-Bus method calls to the system bus. AppArmor mediation in dbus-daemon 1.14 sees the peer process from the container as `(null) (inactive)` and denies the call. This is host-environment behavior and is independent of D-Bus policy and polkit, both of which are already permissive enough on the target host.

Neither D-Bus policy nor polkit are the blocker:
- `/usr/share/dbus-1/system.d/org.freedesktop.ModemManager1.conf` already allows `Introspectable`, `Properties`, and `ObjectManager` for everyone.
- `/etc/polkit-1/rules.d/` is empty on the host, but introspection does not require polkit authorization.

## Scope

Update the production deploy compose file to opt the service out of the docker-default AppArmor profile, and document why this is required and what the security trade-off is.

Out of scope: writing a custom AppArmor profile that whitelists only D-Bus paths needed for ModemManager1 access. That is a future hardening task and should be tracked separately.

## Files to modify

- `deploy/docker-compose.yml`
- `docs/deploy.md`

## Implementation notes

In `deploy/docker-compose.yml`, add a top-level `security_opt` key to the `sms-gateway-v2` service with the single entry `apparmor=unconfined`. Place it next to the existing `restart`, `env_file`, `environment`, `ports`, `volumes` keys. Do not change any other field. Keep ordering consistent with the surrounding service definition.

In `docs/deploy.md`, add a new section titled `AppArmor` (placed after the existing polkit / D-Bus section, or in the same Prerequisites area). The section must:

1. State that on Ubuntu hosts the docker-default AppArmor profile blocks D-Bus method calls from the container to the system bus, including ModemManager1 introspection.
2. Quote the exact error string a user would see on startup so the docs are searchable: `An AppArmor policy prevents this sender from sending this message to this recipient`.
3. Explain that the deploy compose file ships with `security_opt: [apparmor=unconfined]` to bypass this.
4. Document the security trade-off in two sentences: the container loses the docker-default mediation, but it is already privileged with respect to ModemManager (it must talk to the system bus to function), runs as uid 1000 non-root, and has its only published port bound to 127.0.0.1.
5. Mention as a future improvement that a custom AppArmor profile narrowly permitting only the required D-Bus paths can replace the unconfined opt-out.

The docs change must be self-contained prose and must not depend on reading the compose file.

Do not touch any Python source file, any test, any CI workflow, the Dockerfile, or `.env.example`. The fix is deploy-time configuration only. Tests and coverage targets should be unaffected; verify by running the full local CI before opening the PR.
