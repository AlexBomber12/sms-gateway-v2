# PR-024: Add sms_delete_failures_total metric and state field

Branch: feat/pr-024-sms-delete-failures-metric
- Type: feature
- Complexity: low
- Depends on: none
- Priority: 2
- Coder: codex

## Problem

Verified by reading `src/sms_gateway_v2/metrics/registry.py` (all 115 lines) and `src/sms_gateway_v2/relay/relay.py` line 215 to 223. When `delete_message()` raises `MessageDeleteFailed`, the relay catches the exception and emits a `relay_sms_delete_failed` warning log. There is no counter, no gauge, no persisted state field for this event. If delete failures accumulate silently (sticky polkit issue, AppArmor regression, ModemManager storage bug, corrupted rule after upgrade), SMS accumulate in EC25 storage. EC25 storage capacity is limited (30 to 100 messages depending on storage backend). Once full, the network stops delivering new SMS to the modem.

Result: an operator has no visibility into delete failure rate. The failure mode escalates from a log warning to a full SMS outage without any signal that would surface in Telegram heartbeat or `/state` endpoint.

## Scope

Add a Prometheus counter `sms_delete_failures_total` and expose the current value plus the timestamp of the last failure via the relay state so it can be surfaced in the heartbeat (PR-028) and the `/state` endpoint.

Out of scope:
- Making the relay stop on repeated delete failures. Delete failure does not lose the SMS (Telegram delivery already succeeded), so the correct policy is observe and alert, not halt.
- Alerting on delete failure by any channel other than heartbeat and `/state`. Heartbeat surfacing is PR-028.
- Reading EC25 storage capacity via mmcli. The metric is a proxy for storage health; direct capacity read is a separate concern.

## Implementation notes

### Step 1: New Prometheus counter

In `metrics/registry.py`, add near the other counters:

```
sms_delete_failures_total = "sms_delete_failures_total"

self.sms_delete_failures_total = Counter(
    sms_delete_failures_total,
    "Total SMS delete failures from the modem storage after successful Telegram delivery.",
    registry=self.registry,
)
```

### Step 2: Increment the counter and update state

In `relay.py` where `MessageDeleteFailed` is currently caught (around line 215 to 223), after the existing warning log:

1. Increment `self._metrics.sms_delete_failures_total`.
2. Update relay state: set `sms_delete_failures_count += 1` and `last_delete_failure_at = datetime.now(UTC)`.

Both state fields are new. The counter and state update happen even when `fail_on_delete_error=False` (the signal path). For the drain path where `fail_on_delete_error=True`, the exception still propagates as today; also increment the metric and update state before re-raising.

### Step 3: Extend RelayState

In `relay/models.py`, add:

```
sms_delete_failures_count: int = 0
last_delete_failure_at: datetime | None = None
```

Both fields are surfaced in the `/state` endpoint automatically via the existing pydantic serialization. `sms_delete_failures_count` is a monotonic in-process counter (resets on container restart, same behavior as Prometheus counters after restart). This is a deliberate simplification for a homelab deployment.

### Step 4: Log field addition

Extend the existing `relay_sms_delete_failed` log event to include `delete_failures_count` (the post-increment value) so an operator reading logs can see the cumulative count without needing to correlate with metrics.

## Tests

1. `test_delete_failure_increments_metric_on_signal_path`: simulate delete failure in the signal-handler path (fail_on_delete_error=False). Verify the metric counter increments by 1, `sms_delete_failures_count` on state incremented, `last_delete_failure_at` set to a recent timestamp.

2. `test_delete_failure_increments_metric_on_drain_path`: simulate delete failure in the drain path (fail_on_delete_error=True). Verify the metric and state update happen before the exception propagates.

3. `test_delete_failure_log_includes_count`: verify the `relay_sms_delete_failed` log now carries the `delete_failures_count` field with the post-increment value.

4. `test_state_endpoint_serializes_delete_failure_fields`: `GET /state` returns JSON with `sms_delete_failures_count` and `last_delete_failure_at`. When no failures have occurred, count is 0 and last is null.

5. `test_metric_registered_in_registry`: verify `sms_delete_failures_total` is exposed via `/metrics` endpoint after a delete failure occurs, in the expected Prometheus text format.

- `/state` endpoint returns both new fields; existing state fields unchanged.
- `relay_sms_delete_failed` log event now includes `delete_failures_count` field.
- All five tests pass. Existing relay tests continue to pass unmodified.
