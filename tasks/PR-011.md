# PR-011: Wait for SMS Text to populate before reading on MessageAdded

Branch: fix/pr-011-sms-text-race
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 1
- Coder: codex

## Problem

Production deployment of sms-gateway-v2 on EC25-EUX modem reproducibly delivers Telegram messages that contain only the sender number, with the text body empty. Reproduction trace from production logs (2026-05-09):

```
message_added_signal_received modem_path=.../Modem/0 received=True sms_path=.../SMS/0
message_listed modem_path=.../Modem/0 sms_path=.../SMS/0
queue_item_enqueued elapsed_ms=14 item_id=...
relay_sms_enqueued item_id=... sms_path=.../SMS/0
telegram_send_attempt attempt=1
telegram_send_success attempt=1 status_code=200
```

Persisted queue item written to `/app/state/sent/<id>.json` shows:

```
{"sms":{"object_path":".../SMS/0","number":"900","text":"","timestamp":"2026-05-09T20:32:50+03:00","pdu_type":"deliver"},"first_seen_at":"2026-05-09T17:32:51.315274Z","content_hash":"..."}
```

The SMS, still in modem memory because `delete_message` failed on a separate polkit issue, was queryable via `mmcli -m 0 --sms 0` and showed the full text:

```
Content    | number: 900
           |   text: Вход в СберБанк Онлайн в 20:32 по московскому времени. Если входили не вы, позвоните на 900.
```

Number, timestamp, and PduType all read correctly; only the Text property was empty at read time.

## Root cause

ModemManager emits the `org.freedesktop.ModemManager1.Modem.Messaging.Added(path, received: bool)` D-Bus signal when an SMS object is added to storage and the `state` property transitions to `received`. The `received=true` flag indicates state readiness, NOT that the `Text` D-Bus property has been populated. On Quectel EC25 (and likely other modems), Text decoding is performed in a separate async path inside ModemManager and the property is updated via `PropertiesChanged` after the `Added` signal has already been emitted. The race window between signal emission and Text population is on the order of tens of milliseconds; long enough for our handler to call `sms.get_text()` and observe an empty string.

The current code in `src/sms_gateway_v2/modem/client.py:_build_added_handler` already filters on `received=True` (correct), and `list_messages()` reads `Text` via `_read_required("Text", sms.get_text)` immediately. There is no wait or retry. This passes unit tests because they mock the modem and return a populated Text synchronously, but it fails on real hardware.

## Scope

Make SMS Text reads race-free by waiting for the property to populate before treating the message as ready to enqueue. The fix lives in the modem client layer; relay and queue layers must remain unchanged.

Out of scope: redesigning the watch protocol, adding metrics for the wait, refactoring the SmsInterface protocol surface. Only add what is needed to close the race.

## Implementation notes

Add a new method to `ModemManagerClient` that resolves a single SMS path to a fully-populated `IncomingSms`. Call it `read_message` or `get_message`. The implementation:

1. Acquire the SMS interface for the given path via the existing `_get_sms_interface(path)` helper.
2. Read PduType and skip if not in `INBOUND_SMS_PDU_TYPES`. Same gate `list_messages` uses today.
3. Read Text. If non-empty, proceed to read Number, Timestamp, build `IncomingSms`, return.
4. If Text is empty, subscribe to `PropertiesChanged` on that SMS object (interface `org.freedesktop.ModemManager1.Sms`). Wait until either Text becomes non-empty OR the configurable timeout elapses.
5. After the wait, re-read Text. If still empty, log a warning event `sms_text_wait_timeout` with sms_path and configured timeout, and proceed with the empty text (degraded delivery, never block the pipeline). Build `IncomingSms` and return.
6. Always unsubscribe from `PropertiesChanged` before returning, including on exception paths.

Add a setting `MODEM_SMS_TEXT_WAIT_TIMEOUT_SECONDS` to `config.py` and `.env.example`. Default value: `5.0` seconds. The default must be a tunable, not a hardcoded literal in client.py.

Wire the new method into the relay path: replace the call chain `list_messages()` → `_find_sms_by_path` in `src/sms_gateway_v2/relay/relay.py:_process_sms_path` with a single direct call to the new method. The relay should pass `sms_path` directly to the client's new resolver. The full-list scan was a workaround for not having a path-based read; remove it.

Keep `list_messages()` for the recovery path (`_drain_existing_messages` at startup), since that is a different scenario where the SMS has been sitting in storage for some time and Text is guaranteed populated. For consistency, drain may also benefit from the same wait logic, but the race window does not apply there. Decision: leave drain on `list_messages` for now to keep the fix narrow.

The `PropertiesChanged` subscription should follow the same dbus-fast pattern used elsewhere in the codebase. If there is an existing helper for one-shot signal waiting on a path, reuse it; if not, implement it inline in the new method using `asyncio.Event` + signal handler that sets the event when Text changes.

## Tests

Update existing modem client tests:

1. New test: `read_message_returns_text_immediately_if_already_populated`. Mock returns text non-empty on first read; method returns IncomingSms without subscribing to PropertiesChanged.
2. New test: `read_message_waits_for_text_then_returns`. Mock returns empty on first read, then PropertiesChanged emits and second read returns populated text. Method returns IncomingSms with the populated text.
3. New test: `read_message_logs_warning_and_returns_empty_on_timeout`. Mock returns empty on both reads, no PropertiesChanged emitted within timeout. Method logs `sms_text_wait_timeout` and returns IncomingSms with empty text. (This must NOT raise.)
4. New test: `read_message_skips_non_inbound_pdu`. Returns None for non-`deliver` PduType, identical to current `list_messages` filter behavior.

Update relay tests that exercised the path-find pattern: switch them to mocking the new client method.

Coverage must remain at 100 percent on `src/sms_gateway_v2/modem/` and `src/sms_gateway_v2/relay/`.
