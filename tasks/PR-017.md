# PR-017: Auto-enable modem on host boot via systemd unit

Branch: feat/pr-017-modem-auto-enable
- Type: config
- Complexity: low
- Depends on: none
- Priority: 4
- Coder: codex

## Problem

On Ubuntu 24.04 with ModemManager 1.23.4, the Quectel EC25-EUX modem connected to the NAS host (192.168.50.2) does not auto-enable on host boot. After every reboot, `mmcli -m 0` reports `state: disabled` and `signal: 0%`. The relay container starts cleanly but observes a powered-off modem and logs `signal_read percent=0` plus `registration_read registration=unknown` until an operator manually runs `sudo mmcli -m 0 --enable`.

This is a known operational limitation of ModemManager on Ubuntu hosts; the daemon scans devices and registers them in storage but does not transition them out of the disabled state without an explicit enable call. The relay container has no path to fix this from inside its sandbox: enable is a polkit-protected admin action that the polkit rule from PR-013 deliberately does not expose to non-admin callers, and elevating it would defeat the principle of least privilege.

## Scope

Provide a host-side systemd unit that runs `mmcli -m 0 --enable` once after ModemManager is ready, on every boot. Document install steps in `docs/deploy.md`.

The unit must be idempotent (re-running an already-enabled modem is a no-op), tolerate the modem not being present yet (retry briefly), and not block boot if the modem is permanently absent (fail with a logged error, do not loop).

Out of scope: udev hotplug detection (so the unit does not re-enable a modem that was disabled mid-session for diagnostics), supporting multiple modems with arbitrary index, integrating with the relay container in any way, calling the unit from the container.

## Files to modify

- `deploy/systemd/sms-gateway-modem-enable.service` (new)
- `docs/deploy.md`

## Implementation notes

systemd unit body. Place at `deploy/systemd/sms-gateway-modem-enable.service`. The unit:

1. `[Unit]` section: `Description=Enable USB modem after ModemManager is ready`, `After=ModemManager.service`, `Wants=ModemManager.service`, `ConditionPathExists=/usr/bin/mmcli`.
2. `[Service]` section: `Type=oneshot`, `RemainAfterExit=yes`, `ExecStartPre=/bin/sleep 5` (give ModemManager time to scan after its own start), `ExecStart=/bin/sh -c 'for i in 1 2 3 4 5; do /usr/bin/mmcli -m 0 --enable && exit 0; sleep 3; done; echo "modem enable failed after 5 attempts" >&2; exit 1'`.
3. `[Install]` section: `WantedBy=multi-user.target`.

Rationale for the retry loop: on cold boot, `ModemManager.service` reports ready before its internal modem scan completes. The 5 second pre-sleep plus 5 retries with 3 second backoff gives the daemon up to ~20 seconds to populate index 0, which is comfortably more than observed cold-boot scan latency on this hardware (typically 2-8 seconds).

The hardcoded `-m 0` is acceptable for this deployment because the host has exactly one modem and the index is stable across reboots. If a second modem is added in the future, the unit must be revisited.

Operator install steps in `docs/deploy.md` (new section, after "Modem state after host reboot" introduced by PR-016, or merged into that section if PR-016 has been merged):

1. `sudo install -m 0644 deploy/systemd/sms-gateway-modem-enable.service /etc/systemd/system/sms-gateway-modem-enable.service`
2. `sudo systemctl daemon-reload`
3. `sudo systemctl enable --now sms-gateway-modem-enable.service`
4. Verify: `systemctl status sms-gateway-modem-enable.service` should show `Active: active (exited)` after the first run, and `mmcli -m 0` should report `state: enabled` (and shortly after, `state: registered` once the modem associates with the network).

After install, the operator post-reboot manual `sudo mmcli -m 0 --enable` step from PR-016 documentation can be marked as superseded. Update the relevant section in `docs/deploy.md` to point at the systemd unit as the now-recommended approach, while leaving the manual command as a fallback for diagnostic situations.

## Tests

No code changes, no application tests apply. Verification belongs in the operator runbook, not in CI.

The author MUST verify the unit on the production host (or an Ubuntu 24.04 VM with a USB modem) before opening the PR. The verification steps:

1. Install the unit per the documented procedure.
2. `sudo mmcli -m 0 --disable` to set a known-bad starting state.
3. `sudo systemctl restart sms-gateway-modem-enable.service` and confirm `mmcli -m 0` shows `state: enabled` within 10 seconds.
4. `sudo reboot`, log back in, confirm `mmcli -m 0` reports `state: enabled` or `state: registered` without manual intervention.
5. `journalctl -u sms-gateway-modem-enable.service -n 30` shows clean execution and no error lines.

The PR description must state which of these verification steps were performed.
