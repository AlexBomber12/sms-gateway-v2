# PR-025: Reject empty SMS text and retry with bounded backoff

Branch: fix/pr-025-empty-sms-reject-and-retry
- Type: bugfix
- Complexity: high
- Depends on: none
- Priority: 1
- Coder: codex

## Problem

Verified empirically by constructing `TelegramMessage.from_sms(chat_id='123', number='900', text='')` from `src/sms_gateway_v2/telegram/models.py`. The result is a valid `TelegramMessage` with text `<b>900</b>\n` (length 11). The validator does not reject empty SMS text because the formatted body is non-empty. This message is then sent to Telegram and appears in the chat as sender-only with no body.

Verified operationally: this has now recurred in production three times. In each case the modem decoder took slightly longer than the configured `MODEM_SMS_TEXT_WAIT_TIMEOUT_SECONDS` and `read_message` returned an `IncomingSms` with `text=""`. `_process_sms` enqueued the item, worker sent it to Telegram, `delete_message` removed the SMS from EC25 storage. The SMS content is now permanently lost. The operator sees only the sender number in Telegram.

Two independent fixes are needed together:

1. `TelegramMessage.from_sms` must reject empty text so the failure surfaces as an exception in the enqueue path rather than as a silently-delivered empty message.
2. The read path must retry with bounded backoff so the modem gets more opportunities to decode Text before the SMS is treated as undecodable and dropped.

Even a very generous timeout in step 1 alone is not sufficient because decoder tail latency is not bounded by anything we control.

## Scope

Two coordinated changes:

1. `read_message` returns `None` when Text is still empty at the end of the timeout, instead of returning an `IncomingSms` with empty text.
2. `_on_new_sms` handler in relay schedules a bounded retry when `read_message` returns `None`. If all retries exhaust, the SMS is marked undecodable, a warning is logged, the metric is incremented, and the SMS is deleted from modem storage (to avoid EC25 storage exhaustion).

The delete decision after undecodable-exhaustion is deliberate: keeping the SMS in EC25 storage would risk overflow, which stops all future SMS delivery from the network. Losing one undecodable SMS is preferable to losing all subsequent SMS.

Out of scope:
- Changing `MODEM_SMS_TEXT_WAIT_TIMEOUT_SECONDS` default (operators tune this per-hardware).
- Changing the `list_messages` path used by drain (see PR-027 which addresses drain race).
- Adding placeholder text like `(empty body)` in Telegram. The choice is retry-till-decoded, not placeholder.

## Implementation notes

### Step 1: Reject empty text in TelegramMessage.from_sms

In `telegram/models.py`, `TelegramMessage.from_sms` must raise `ValidationError` when `text` is empty or whitespace-only. Existing signature stays: it takes `chat_id`, `number`, `text`. The empty-check happens before body formatting:

```
if not text or not text.strip():
    raise ValueError("SMS text is empty; refusing to build TelegramMessage")
```

Wrap into pydantic `ValidationError` if the surrounding code expects that type; check existing pattern in the file.

### Step 2: read_message returns None on undecoded Text

In `client.py`, the current `read_message` (lines around 444 to 511) returns an `IncomingSms` with empty text after the timeout warning. Change the final branch: if `text == ""` after the polling loop exhausts, keep the existing `sms_text_wait_timeout` warning log, then return `None` instead of the `IncomingSms`.

### Step 3: New settings for retry policy

In `config.py`, add:

```
modem_sms_text_undecoded_retry_max_attempts: int = Field(default=3, ge=1, le=10)
modem_sms_text_undecoded_retry_delay_seconds: float = Field(default=30.0, ge=5.0, le=300.0)
```

Defaults chosen from operator preference: 3 retries at 30 second intervals. Total worst-case latency for a fully-decoded SMS: initial timeout plus 3 retry-delay plus 3 retry-timeouts. Concretely with `text_wait_timeout_seconds=15` this is 15 plus 90 plus 45 equals 150 seconds. Acceptable for OTP delivery (typical validity 5 minutes).

### Step 4: Retry orchestration in relay

The natural place for retry state is inside the incoming handler on `SmsRelay`. Introduce an asyncio.Task per SMS path that:

1. On first `read_message` returning None, schedule a delayed retry via `asyncio.create_task` after `modem_sms_text_undecoded_retry_delay_seconds`.
2. On retry: call `read_message(sms_path)` again. If populated Text is now present, proceed as with a normal SMS: enqueue and delete.
3. If still None: increment attempt counter. If attempts less than `modem_sms_text_undecoded_retry_max_attempts`, reschedule. If exhausted, log `sms_text_undecodable` (error), increment `sms_text_undecoded_total`, delete the SMS from modem storage, and stop.

Track pending retries in a dict `self._pending_text_retries: dict[str, asyncio.Task]`. On task completion or cancellation, remove the entry. On relay shutdown, cancel all pending tasks. This guarantees no leaked tasks.

Include a lock or per-path serialization so that concurrent MessageAdded firings for the same path do not create duplicate retries. Reuse `self._sms_handler_lock` if it already protects this section; otherwise introduce a per-path in-progress set.

If the SMS path disappears mid-retry (e.g. after a modem reset), catch `MessageReadMissing` (or whatever the existing error class is) and stop the retry cleanly with a log event.

### Step 5: New metric

In `registry.py`, add:

```
sms_text_undecoded_total = "sms_text_undecoded_total"

self.sms_text_undecoded_total = Counter(
    sms_text_undecoded_total,
    "Total SMS dropped because Text remained empty across all decode retries.",
    registry=self.registry,
)
```

Increment only on final exhaustion, not on individual retry attempts.

### Step 6: Log events

- Keep existing `sms_text_wait_timeout` (warning) inside `read_message`.
- New `sms_text_undecoded_retry_scheduled` (info) fields: `sms_path`, `attempt`, `delay_seconds`.
- New `sms_text_undecoded_retry_recovered` (info) fields: `sms_path`, `attempts_used`, `total_wait_seconds`.
- New `sms_text_undecodable` (error) fields: `sms_path`, `total_wait_seconds`, `attempts_used`.
