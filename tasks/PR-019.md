# PR-019: Permit term and kill signals from runc in AppArmor profile

Branch: fix/pr-019-apparmor-signal-types
- Type: bugfix
- Complexity: low
- Depends on: none
- Priority: 4
- Coder: codex

## Problem

After PR-014 (custom AppArmor profile) and PR-018 (Sms wildcard removal), the production deployment continues to log AppArmor signal denials whenever the container is stopped or recreated. Observed on 2026-05-10 immediately after `docker compose -p sms-gateway-v2 up -d --force-recreate`:

```
audit(...:153): apparmor="DENIED" operation="signal" class="signal"
  profile="sms-gateway-v2" pid=272129 comm="runc"
  requested_mask="receive" denied_mask="receive" signal=term peer="runc"

audit(...:154): apparmor="DENIED" operation="signal" class="signal"
  profile="sms-gateway-v2" pid=272148 comm="runc"
  requested_mask="receive" denied_mask="receive" signal=kill peer="runc"
```

Root cause. The current profile contains:

```
signal (receive) peer=unconfined,
signal (send,receive) peer=sms-gateway-v2,
```

The `receive` rule for `peer=unconfined` is meant to allow signals from runc (which runs unconfined) to the container process (which runs under the `sms-gateway-v2` profile). However, on AppArmor 3.x the `signal` rule without an explicit `set=(...)` specifier does NOT match arbitrary signals; it matches only signals without a typed set, which is empty in practice. The result is that SIGTERM and SIGKILL from runc during container shutdown are denied.

In practice, container shutdown still completes because Docker has multiple kill paths: cgroup freezer kills and kernel-level init reaping bypass AppArmor signal mediation. The container does NOT lose data because the queue is persisted on disk before any in-flight item is consumed. But:

1. The `docker stop` operation incurs the full grace timeout (10 seconds default) on every recreate, because the SIGTERM that would normally trigger Python's graceful shutdown handler never reaches the process.
2. Each shutdown emits a pair of `DENIED` audit entries, which clutters `dmesg` and is visible in any audit log review.
3. The escape claim in `docs/deploy.md` that "absence of fresh DENIED entries after the recreate is the expected state" is currently false; the docs and the runtime disagree.

This is a clean, well-understood single-line fix.

## Scope

Update the AppArmor profile to explicitly enumerate the signal types that should be permitted from runc and from peer instances of the same profile. After the change, container start, stop, and recreate produce zero `DENIED` entries in `dmesg | grep -i apparmor`, and `docker stop` completes promptly when the application's signal handler responds.

Out of scope: any other profile change (Sms interface narrowing was completed in PR-018 and is already correct), any docs change (the existing AppArmor section already covers operator install/verify and the verification claim becomes accurate after this fix), any change to the application's signal handling (Python's existing default + uvicorn graceful shutdown is what we want runc's SIGTERM to reach).

## Files to modify

- `deploy/apparmor/sms-gateway-v2`

## Implementation notes

Replace the two existing signal rules:

```
signal (receive) peer=unconfined,
signal (send,receive) peer=sms-gateway-v2,
```

with explicit signal-set forms covering the signals runc actually sends during container lifecycle, plus the per-process control signals our own profile peers may exchange:

```
# runc sends SIGTERM at docker stop start, SIGKILL after the grace timeout,
# and may also send SIGCONT/SIGSTOP during pause/unpause flows. Without an
# explicit set=(...) clause AppArmor 3.x denies these even though peer is
# unconfined, which slows graceful shutdown and clutters dmesg with
# apparmor="DENIED" entries.
signal (receive) set=(term, kill, cont, stop, hup, int, quit, usr1, usr2) peer=unconfined,
signal (send, receive) set=(term, kill, cont, stop, hup, int, quit, usr1, usr2) peer=sms-gateway-v2,
```

The set is broader than just `(term, kill)` deliberately: SIGHUP/SIGINT/SIGQUIT are used by typical orchestration tooling (compose down with Ctrl-C, manual `docker kill --signal`), SIGCONT/SIGSTOP are part of `docker pause`/`docker unpause`, and SIGUSR1/SIGUSR2 are common application-level tunables that operators may want to reach the process for log rotation or runtime knobs. None of these signals are dangerous to permit at the AppArmor layer; the application chooses which to handle in user code.

The comment block above the rules is required so a future maintainer who reduces the set understands why the broader form is intentional. Do not skip the comment.

## Tests

No application code is touched; profile changes are not exercised by CI.

The author MUST verify on the production NAS host:

1. Install the updated profile: `sudo install -m 0644 deploy/apparmor/sms-gateway-v2 /etc/apparmor.d/sms-gateway-v2 && sudo apparmor_parser -r -W /etc/apparmor.d/sms-gateway-v2`. The parser must accept the rules cleanly with no warnings.
2. Confirm the profile is loaded in enforce mode: `sudo aa-status | grep sms-gateway-v2` shows the profile and at least one process running under it.
3. Recreate the container: `cd deploy && docker compose -p sms-gateway-v2 up -d --force-recreate`. The recreate should complete in noticeably less time than the prior 10+ second grace window because SIGTERM now reaches the application.
4. After recreate is done, check `sudo dmesg -T | grep -i apparmor | tail -10`. There MUST be no fresh `apparmor="DENIED"` entries from the recreate. The only entry should be a `STATUS operation="profile_replace"` line confirming the load.
5. Send a real or test SMS through the modem and verify end-to-end delivery to Telegram. This is the same smoke test used to validate PR-018; it confirms that narrowing the signal rule did not regress anything else.

The PR description must record which of these verification steps were performed and what the recreate duration was (rough seconds).
